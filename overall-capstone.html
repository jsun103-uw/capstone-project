Overall Capstone

Project selection

The inspiration for this project came a few weeks prior to my capstone course, while brainstorming projects. I needed something simple enough to build within 2 quarters, so I thought of the .io genre. Games such as agar.io and diep.io achieved massive popularity in the mid 2010s with their simple mechanics that allowed for a high skill ceiling.

I had previously also enjoyed playing foxhole, a trench warfare game where players played as a cog in the war machines of two competing powers, where the outcome of battles were dictated by dozens to hundreds of players running various defensive, offensive, and logistical tasks. That was the inspiration for this project, a trench warfare game in the style of a .io game.

As I am looking to join a role as an software developer, the backend architecture and systems of the game would show my ability to design applications. While not as direct a parallel as developing a tool to fix a problem, the benefit for this capstone is that it would be much easier for me to maintain the motivation to work on the project, as game development has long been a hobby of mine.

Scheduling Issue

At the start of the capstone project when I had to schedule the expected time it would take to develop, I drastically underestimated the amount of time it would take to develop features by 2-3 fold. This was due to my inexperience in network applications, as I had only developed a multiplayer game before using raw sockets, and based the estimates on the time it took to develop singleplayer features. I incorrectly assumed that a mid-level library would allow me to move with a similar speed. Compounding this issue were the capstone assignments, which reduced the amount of hours I had to actually work on the game further from the 300 expected hours for the capstone.

The next feature I needed to learn was 3D game development, as this was my first 3D game. Simple concepts like exporting a cube from blender took a while to learn due to my unfamiliarity, so it quickly became evident that my schedule estimates would need to be revised for creating 3D textures and animations.

Utilizing Feedback

This project required me to seek a lot more feedback compared to previous works, the benefits of which became evident after I had an initial prototype working. It was very useful in terms of supplementing my weaknesses and validating design choices, such as in user interface design. My peers were able to quickly identify issues in my design so I could improve navigation. In turn, I also provided feedback on a workout application that improved usability.

Reflecting on Failures

Overscoping seemed to be a very persistent issue. Early on I decided to accept more technical debt to prototype features faster, however ultimately I still made several frameworks that largely went unused. There was a chunk system meant to support very large maps that was replaced by a simpler 2D tile grid as it was unwieldy to extend behavior with new components such as adding structures. I created an ability system, but so far the game only has one ability.

When the prototype neared completion, it became apparent that I would likely need to sacrifice either the style of the game or the gameplay as I underestimated the difficulty of 3D texturing. Reflecting on how this could have been avoided, I could have used mock-ups and requested stakeholder feedback from them initially. I decided on migrating to a 2D tilemap, which took some time but was considerably easier to add textures and sprites for the tiles and characters.

It was also around this time that my feature development time estimates became more accurate as I became more familiar with the time overhead of network programming and as I became more familiar with implementing network features. One thing that helped was breaking down tasks further. Whereas at the beginning, I was making estimates in the range of 4-5 hours to complete a use-case level feature, later I would split the feature into tasks so making estimates would be easier.

Next Steps

During this project, I practiced 3D game design, network programming, and project management. I can use this game as a demonstration of my skills for a future career in application development, especially network applications.

I will wait until Godot4 updates to support mono webassembly exports, which would make it easier for people to review my work online by opening the project in the browser. The game has enough features to be considered playable. I found that multiplayer game development was less enjoyable than singleplayer development, partly due to the increased complexity, and partly due to my personal gaming preferences, so I will be moving on to my next project using what I learned in this project.
